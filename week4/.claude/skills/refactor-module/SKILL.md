# Refactor Module

重構任意程式檔或模組的skill。目標:改善結構,行為完全不變。

## 核心原則

重構跟加功能是兩件事,不要混在一起做。重構過程中若發現bug或缺少的功能,記下來但不要順手修——先完成純結構重構,再另外跟使用者確認要不要處理那些額外發現。這樣diff才乾淨,行為對照才可信。

## 執行步驟

### 1. 讀懂目標檔案/模組

先完整讀過目標檔案,搞懂現有職責邊界。若模組有對應測試(`backend/tests/`底下同名或相關測試檔),一併讀,這是重構後拿來核對行為沒變的依據。

### 2. 找出重構動機

常見的重構訊號,依實際狀況挑相關的:
- 函式過長,一個函式做了多件不相關的事
- 重複邏輯出現在多處
- 命名模糊,看名字猜不出用途
- 職責混雜(例如I/O邏輯跟業務邏輯寫在一起)
- 過深的巢狀`if`/迴圈
- 魔術數字或字串散落各處

不要為了重構而重構——沒有實際壞味道的程式碼,維持原樣。

### 3. 規劃再動手

在心裡(或簡短跟使用者說明)列出打算怎麼拆:哪些邏輯要抽成獨立函式、要不要調整檔案內排列順序、命名打算怎麼改。避免邊改邊想,容易改到一半發現方向不對,浪費一輪。

### 4. 套用修改,保持行為不變

用`Edit`逐步套用。每一步都自問:這一步是否只改了「怎麼做」,沒有改「做出什麼結果」?公開的函式簽名、回傳值、API路由行為,除非使用者明確要求,否則維持不變。

### 5. 跑lint/format,確認乾淨

重構完後,在對應的`weekN/`目錄下跑:

```bash
make format   # black . && ruff check . --fix
make lint     # ruff check .
```

若不是在有Makefile的week目錄下(例如通用場景、非本repo的其他專案),改用該專案慣用的format/lint指令;找不到慣例就跳過這一步並告知使用者。

### 6. 交付前的行為核對

若目標模組有既有測試,重構後跑:

```bash
pytest -q backend/tests/test_xxx.py
```

確認全數通過,沒有因結構調整動到行為。若沒有現成測試覆蓋到重構的部分,明確跟使用者說「這塊沒有測試保護,行為對照靠人工檢視」,不要假裝有把握。

### 7. 總結交付

簡短說明:改了哪裡、為什麼這樣拆、行為有沒有變(應該沒有)。這段內容剛好可以直接餵進`writeup.md`的「Before vs. after」區塊——如果使用者是在week4的自動化情境下用這個skill,提醒他們補進writeup。
